## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/clipseg_segmentation_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `CLIPSegForImageSegmentation`/`CLIPSegProcessor`. The upstream `pytorch_model.bin` is not listed and not used; the notebook's only external dependencies are the pinned PyPI distributions and the Hub at the model revision.
- **Role stages:** `validate_inputs` writes `outputs/clipseg_segmentation_input_manifest.json` with the schema (352×352 resize, sigmoid, resampling, thresholding), the ceilings, the input's observed mode and size, the normalised phrases, the threshold, the verdict, and one recorded rejection finding from the duplicate-phrase probe; `evaluation_report` writes `outputs/clipseg_segmentation_evaluation_report.json` — `sample-sanity` with one `mask_iou` entry per drawn shape (reference and predicted area fractions) and their mean `miou` on the synthetic scene; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 640×480 scene drawn in code with Pillow (no text rendering, so its digest is stable across Pillow builds) whose drawing calls also produce the boolean reference masks — the same scene the smoke run used; `mask_iou` against masks you drew yourself is sanity evidence for the input contract, resize, decoder, sigmoid, resampling and thresholding, not a segmentation metric. Two phrases naming absent things (`a cat`, `the sky`) are included so the notebook shows an empty mask alongside found ones; the smoke run's IoUs (0.91–0.96 at 0.5) are recorded in the notebook prose.
- Score semantics (UNC1–UNC4): the per-pixel probability is an uncalibrated sigmoid and masks are independent per phrase; the notebook says so before the first mask and again in the interpretation section, and states that an absent phrase is not guaranteed an empty mask. The threshold is a caller-owned request parameter exposed as a `# @param` value (default `MASK_THRESHOLD = 0.5`, with the smoke run's 0.3/0.5/0.7 IoUs quoted) and passed explicitly on the `segment` call. The notebook performs no validation of its own — image, phrases and threshold are checked only by the pipeline's `validate_inputs`/`segment` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `LOGIT_SIZE` (352), `MAX_PROMPTS` (16), `MAX_PROMPT_CHARS` (64), `MAX_TEXT_TOKENS` (77) and `MASK_THRESHOLD` (0.5) are printed before the model runs.
- CPU is documented as adequate (card-measured 5.0 s load, 0.82 s for six phrases on the 640×480 scene, 0.15 s for one; 0.42 s on a 4096×4096 blank image); the notebook states that cost is per phrase and that GPU masks need not match CPU masks at the boundary.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
